Applying to jobs means typing the same answers into the same forms, over and over. I wanted a tool that automated that repetitive process, without ever putting words in the applicant's mouth.

During my software engineering internship at a career-tech startup, I designed and built an AI Chrome extension to autofill job applications across LinkedIn Easy Apply, Indeed, Internshala, Lever, and Workday directly from a user's verified candidate profile. Over six months, I developed the project from initial prototype through production releases on the Chrome Web Store.

A lot of autofill tools try to fill every field they can. I built this on the opposite idea. A wrong answer, submitted to an employer under your name, is worse than a blank one.

**At a glance**

- Five portals, built in vanilla JavaScript with zero runtime dependencies
- A four-rung answer ladder that never guesses numbers or yes/no answers
- 152 end-to-end checks in a real browser, plus 21 offline test suites
- Workday support shipped post-launch without disabling existing installs

## The rule: refuse to guess

A made-up "5 years of experience" or a wrong "Yes" on an eligibility question can cost someone a job. Every application goes to an employer under the user's name, so a confident wrong answer is the most expensive failure the product can have. I decided that up front, treated it as the core requirement, and the extension follows three rules because of it.

| Field type | What the extension does |
| --- | --- |
| Numbers and yes/no questions | Answers only from the profile. No profile value means no answer. |
| Dropdowns and radio options | Scores every option and picks one only above a confidence threshold. |
| Applicant-only questions (criminal record, consents, non-competes, passport) | Never answered. Always left for the applicant. |

AI writes only descriptive text, like a cover note or a role description. On every portal, the extension highlights the Submit button and stops, ensuring the final review and submission click remains strictly with the user, keeping every interaction explicitly user-initiated.

The deliberate trade-off is a lower fill rate on unfamiliar forms. A blank field is visible and easily completed by the applicant, while an incorrect hallucination is silent and costly. In testing and production benchmarks, the extension consistently achieved a ~95% accurate fill rate, leaving only ambiguous or applicant-specific questions for manual completion.

## The answer ladder

For every field, the extension climbs down a ladder and stops at the first rung that has a trustworthy answer. The order matters more than anything else here. What you said yourself always wins, and AI only gets a turn when nothing else has an answer.

The ladder turned a vague "fill the form with AI" into precedence rules I could test field by field. It also makes every filled value traceable to the rung that produced it.

The first and third rungs both remember answers, but they hold different scopes. The first rung lives in local browser storage and only ever retains answers the user typed manually. The third is a persistent backend answer store: one saved answer per question family, whether sourced from manual input, verified profile fields, or validated model completions, allowing cross-portal reuse. Both stores are isolated per user and keyed on a cryptographic hash of the normalized question string. Saved answers generated by the system or model undergo validation before reuse: applicant-only questions are excluded, and conflicting figures (such as compensation numbers) are discarded. Generative AI is strictly a last resort since most fields resolve deterministically from verified profile data.

## Learning from what users type

The top rung only works if the extension learns. When the tool leaves a field blank and the applicant fills it in, that answer gets saved and reused the next time the same question, or a very similar one, appears.

The hard part is telling those two kinds of input apart, because the script and the user change the same fields and fire the same browser events. I went with provenance per element instead of a global "extension is filling" flag. Every time the extension writes to a field, it records the exact value in a `WeakMap` keyed on that element. An input event counts as the user's only if the value differs from what the tool wrote. A global flag can drift when fills nest across async steps on multi-page forms, but a per-element record can't. The `WeakMap` also lets the browser clean up entries when a form page goes away.

## Filling React-controlled inputs

Most job portals are React apps, and React ignores a value set directly on an input because its internal state never sees the mutation. To solve this, the extension sets each value through the browser's native property setter on `HTMLInputElement.prototype`, and then dispatches synthetic `input`, `change`, and `blur` events so validation libraries treat it as a genuine edit. Asynchronous comboboxes and dynamic typeahead inputs each get specialized synchronization routines to ensure suggestion menus properly mount, filter, and commit selections before moving to the next field.

## Handling portal redesigns

Third-party job application flows frequently update their DOM structures. When a major portal updated its modal architecture, existing class-based form detection broke.

To debug this cleanly, I isolated the portal's live markup by capturing multiple application steps as sanitized HTML fixtures. Testing against these fixtures revealed that the portal had moved its modal flow into a native HTML `<dialog>` element and switched to dynamic, build-hashed CSS class names.

Instead of playing cat-and-mouse with brittle CSS selectors, I rebuilt detection on durable semantic and accessibility signals that portals rarely change without breaking screen readers: dialog landmark roles (`role="dialog"`), `aria-label` attributes, form progression headers, and standard button text. Because browsers treat injected content outside modal dialogs as inert, the extension's UI widget was mounted directly inside the dialog element.

To catch external DOM shifts before users ever see them, I built an automated end-to-end testing harness. It loads the compiled extension in headless Chromium, serves local fixture snapshots of each supported portal, and asserts that fields populate accurately while verifying that Submit is never clicked automatically. It runs 152 checks across the five portals.

## Adding Workday without breaking a single install

Workday is one of the most widely used application systems, and supporting it came with a trap. In Chrome, a new required host permission disables the extension for every existing user until each of them accepts it.

| Option | Result for existing users |
| --- | --- |
| Add Workday as a required permission | Extension disabled until they re-accept |
| Leave Workday out | Nothing breaks, but no Workday support |
| **Make Workday an optional permission** | **Nothing breaks; users turn Workday on with one click** |

Existing users were the deciding factor, so I shipped the third option. The widget nudges users to turn Workday on, and that opens the popup with a one-click "Turn on". Until the user opens the popup, a "NEW" badge points them to it. Existing installs updated silently.

The permission covers Workday's job domains (`*.myworkdayjobs.com` and `*.myworkdaysite.com`). Chrome only grants it from an explicit user gesture, which is why the nudge routes through the extension popup rather than prompting spontaneously. Once granted, the extension dynamically registers the portal content script on the fly, and unregisters it if permission is revoked.

## Security and speed by design

An extension runs inside pages it doesn't control, holds a user's session and triggers paid AI calls. I treated all three as design constraints from day one.

- The session token never touches the page DOM. Only the background service worker retains authentication tokens, and content scripts communicate via an isolated message proxy that rejects token inspection requests.
- No secret API keys ship in client bundles. AI calls route through an authenticated backend gateway, which manages keys and enforces per-user rate limits via rolling usage quotas.
- Page text is treated as untrusted input. Job descriptions and form labels are sanitized, stripped of prompt-injection delimiter sequences, truncated to safe character bounds, and passed into toolless inference endpoints with strict JSON schema validation. Every completion is validated against field constraints before insertion, and the applicant reviews every answer before submission.
- Extension permissions remain strictly minimal: only `storage` and `scripting`, protected by automated manifest build gates.
- An automated circuit breaker temporarily halts AI requests upon consecutive backend timeouts, ensuring that multi-question forms fail gracefully with clear feedback rather than hanging indefinitely.

## Trade-offs and what's next

- Per-portal DOM adaptation is the trade-off for high reliability. It keeps behavior deterministic and inference costs low, but requires ongoing maintenance as portals evolve. A future iteration could extract structural form schemas and map them with generalized heuristics.
- Question normalization currently executes in the client script; offloading semantic clustering to a backend service would allow matching rules to evolve without requiring client extension updates.
- Session bridging: Synchronizing authentication with the web platform provides seamless onboarding, though standalone token refresh would improve offline resilience.
- Expanding coverage: The core engine currently handles five major platforms, with architecture in place to expand to additional enterprise applicant tracking systems (ATS).

If a friend told me they were building an autofill extension, I'd tell them to decide what the tool must refuse to do before deciding what it should fill. That one rule shaped every other decision in this extension.

## Built with

The extension is built on [Manifest V3](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3), Vite with [@crxjs/vite-plugin](https://crxjs.dev) and vanilla JavaScript with zero runtime dependencies, backed by FastAPI, Postgres and Supabase auth, with Gemini for descriptive answers and [Puppeteer](https://pptr.dev) for end-to-end tests.
