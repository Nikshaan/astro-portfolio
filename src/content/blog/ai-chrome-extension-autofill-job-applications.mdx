At Mentoria, I built the Chrome extension for Arya, an AI job-search platform. It fills job applications on LinkedIn, Workday and three other portals using the user's Arya profile.

Filling forms sounds simple until you think about what a wrong answer means. A blank field is visible, and the user can fix it in seconds. A confident wrong answer can reach an employer under the user's name.

That gave the extension one rule: **never guess on the user's behalf**. Most of the architecture exists to enforce it.

## The architecture

The extension has three main parts, and each one has a separate job:

- **Content scripts** run inside each portal. They detect the form, fill its fields and confirm the values were written.
- **The service worker** handles communication with the backend. Page scripts and content scripts don't get direct access to the user's session.
- **The backend** provides profile data and saved answers, and makes every LLM call. No model API key ships with the extension.

[Chrome](https://developer.chrome.com/docs/extensions/mv3) can stop a [Manifest V3](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3) service worker whenever it's idle, so I couldn't keep important state in global variables. State lives in [`chrome.storage`](https://developer.chrome.com/docs/extensions/reference/api/storage), and each wake-up is treated as a cold start.

## The answer ladder

I didn't want one big "fill this form with AI" step. Instead, every field goes through a fixed order of sources and stops at the first trustworthy answer:

The order matters. Something the user typed always wins, and the model only gets a turn when nothing else has an answer.

Some rules sit outside the ladder:

- **Numbers and yes/no answers** come only from trusted user data, never from the LLM.
- **Dropdowns** are selected only when an option is a confident match.
- **Applicant-only questions**, such as legal declarations and consent, are left for the user.
- **Submit** is never clicked by the extension.

Each filled value also keeps track of the source that produced it. This made behaviour much easier to test, because I could check the expected source field by field.

## Matching the same question across portals

Different portals ask the same thing in different ways. "Notice period", "What is your notice period?" and "Notice period (in days)" should map to one answer.

I normalize each question before comparing it: remove filler words and formatting hints, then map common phrasings to a standard form. Saved answers use a hash of that normalized text.

Answers the user typed can also match through fuzzy similarity, but only behind strict checks. If two questions differ in something like a number, a negation, a location or the intent behind the question, they don't match, even when most of their words are the same.

I tuned this for precision over recall. Missing a match means the user types an answer once. A false match puts the wrong words in their application.

## Filling modern forms

Writing to an input isn't always enough. [React](https://react.dev) tracks an input's value itself, so a direct assignment can update the DOM without updating the component's state.

The fix is to call the browser's native setter and then dispatch the events the form expects:

```javascript
function setNativeValue(element, value) {
  const prototype = element instanceof HTMLTextAreaElement
    ? HTMLTextAreaElement.prototype
    : HTMLInputElement.prototype;

  const setter = Object.getOwnPropertyDescriptor(prototype, "value").set;
  setter.call(element, value);

  element.dispatchEvent(new Event("input", { bubbles: true }));
  element.dispatchEvent(new Event("change", { bubbles: true }));
  element.dispatchEvent(new Event("blur", { bubbles: true }));
}
```

Dropdowns, comboboxes and typeaheads each needed their own handling. A field only counts as filled after the extension reads the value back from the page.

## Learning from the user's edits

When a user fills a field the extension left blank, that answer should be available next time. The problem is that the extension and the user both change the same fields and trigger the same events.

A global "the extension is filling" flag can drift across async steps and multi-page forms. Instead, I record the exact value written to each element in a `WeakMap`:

```javascript
const extensionValues = new WeakMap();

function fill(element, value) {
  setNativeValue(element, value);
  extensionValues.set(element, value);
}

document.addEventListener("input", (event) => {
  const element = event.target;
  if (extensionValues.get(element) === element.value) return;
  learnUserAnswer(element);
}, true);
```

If the current value differs from what the extension wrote, the change came from the user. When a form page goes away, its elements can be garbage-collected, and the `WeakMap` entries go with them.

## Keeping the LLM in its lane

Before any LLM call, the backend authenticates the request, applies usage limits and uses its own copy of the profile instead of trusting profile data sent by the client. Questions the model shouldn't answer are refused before the call is made.

Page text is untrusted, since a job description could contain instructions aimed at the model. The prompt fences that text as data, and the model has no tools. Its output is validated before being filled, and the user reviews everything before submitting.

If the AI backend starts failing, a circuit breaker pauses calls for a short time. The affected fields stay blank, so the rest of the form still works.

The captured pages took the live site out of the picture. An older working build failed on them too, which pointed to LinkedIn's markup rather than my latest code.

The form had moved into a native `<dialog>`, and its class names were now generated hashes. Instead of replacing old selectors with new brittle ones, I rebuilt detection around header text, ARIA labels, progress roles and button text.

Fixing that exposed a second bug. An open modal makes the rest of the page inert, so a widget outside the dialog couldn't be clicked. Moving the widget inside the dialog fixed it.

## Shipping without breaking installs

Adding a new required host permission can disable an extension for existing users until they accept it. Workday support could have caused exactly that.

I made Workday an optional permission instead. Existing installs update normally, and users can turn Workday on with one click. Once access is granted, the extension registers the Workday content script at runtime.

Testing follows the same approach of removing outside dependencies. [Puppeteer](https://pptr.dev) loads the real built extension into headless [Chromium](https://www.chromium.org/chromium-projects/) and runs it against captured copies of each portal. Every end-to-end check also confirms that Submit was never clicked.

CI runs linting, formatting, offline tests and the store build on every pull request. The build also includes a permission gate that fails if the extension's permissions change unexpectedly, so a risky permission can't reach users by accident.
