Arya's frontend was a client-side [React](https://react.dev) app on a static host. For users, that worked fine. For search engines, the first HTML response was mostly an empty shell, with the content only appearing after JavaScript ran.

I needed to add a blog that could rank on Google, with a few constraints:

- It had to live under `/blog` on the main domain.
- It couldn't use a third-party CMS.
- It couldn't add a new hosted service.

The static host created its own problem. It couldn't generate pages per request, return a real 301 redirect or return a real 404 for an unknown URL.

So I took every decision a server would normally make and moved it into the build.

## The architecture

The system has three parts: a CMS for writing, a publish pipeline for triggering builds, and a static build that produces the finished site.

Everything fit inside the existing stack. [FastAPI](https://fastapi.tiangolo.com), [Postgres](https://www.postgresql.org), [Redis](https://redis.io) and [Celery](https://docs.celeryq.dev) were already there, and the frontend build could do the rest.

## Storing a post

Writers use a [TipTap](https://tiptap.dev) editor with draft and publish states, categories, image uploads and SEO fields for each post.

Each post is stored in two forms:

- **TipTap JSON** is the source of truth, so the editor can reopen exactly what was saved.
- **Sanitized HTML** is a cache used for rendering.

The backend renders the JSON once, adds heading IDs for the table of contents, and sanitizes the result with [`nh3`](https://nh3.readthedocs.io). The sanitizer uses an allowlist, so any tag or attribute that isn't explicitly allowed gets removed. This keeps a writer's content from running as a script in a reader's browser.

## Prerendering the real pages

At build time, a script fetches the published posts and renders the actual React blog pages to static HTML. Crawlers and readers get content from the same components, so there's no separate SEO version of the site to maintain.

Each post gets its own:

- Title, meta description and canonical URL
- [Open Graph](https://ogp.me) tags for link previews
- `Article` structured data in [JSON-LD](https://json-ld.org)
- Table of contents
- Sitemap entry

The build fetches posts with bounded concurrency and request timeouts. That keeps it from overwhelming the API, and one stuck request can't hang the build forever.

## Keeping hydration clean

Once the HTML loads, React takes over the page in a step called hydration. If the static HTML doesn't match what React would render, React can discard it and render again, causing flicker and wasted work.

I ran into three causes and fixed each one:

1. **Missing CSS.** [Vite](https://vite.dev) gives CSS files hashed names, so the prerender step reads Vite's build manifest and injects the correct file.
2. **Different component trees.** Blog routes load eagerly, so the build and the browser render the same tree.
3. **Different dates.** A date could format differently on the build machine and in the reader's browser, so I pinned formatting to one time zone.

## Redirects and 404s without a server

A static host can't make decisions per request, so the build generates files for those cases ahead of time.

When a post's slug changes, the old slug goes into a slug history table. The next build creates a small page at the old URL that sends visitors to the new one. It isn't a true 301, but it's the closest option on a static host.

Removed posts get a `noindex` page, so they can drop out of search results. Index, pagination and category pages also link to every published post, which means posts aren't reachable only through the sitemap.

## Publishing without a manual deploy

"Publish" had to mean live, without anyone running a deployment. But rebuilding on every click would waste builds, because writers often publish and then fix a few typos right away.

The pipeline uses Redis to track changes and Celery to run the build later:

Redis holds a version counter, the last built version and a flag showing that a build is already scheduled:

```python
def on_publish_or_edit():
    try:
        redis.incr(VERSION)
        if redis.set(SCHEDULED, 1, nx=True, ex=FLAG_TTL):
            rebuild.apply_async(countdown=DEBOUNCE_SECONDS)
    except RedisError:
        trigger_deploy_hook()
```

`SET NX` only succeeds if the flag doesn't exist, so only the first change in a window schedules a build. Later edits just increase the version. The countdown doesn't restart, so someone who keeps editing can't postpone the build forever.

When the task runs, it clears the flag and compares the two versions:

```python
@app.task(bind=True)
def rebuild(self):
    redis.delete(SCHEDULED)
    target = int(redis.get(VERSION) or 0)
    built = int(redis.get(BUILT) or 0)

    if target <= built:
        return

    try:
        trigger_deploy_hook()
    except Exception as error:
        raise self.retry(exc=error)

    redis.set(BUILT, target)
    follow_up.apply_async(countdown=FOLLOW_UP_SECONDS)
```

A few details make this reliable:

- **Clearing the flag first** lets an edit made during a build schedule its own rebuild.
- **The built version updates only after the hook succeeds**, so a failed trigger can be retried without losing the change.
- **The version check makes the task idempotent.** Celery can run a task twice in some failure cases, and the second run exits if nothing is new.
- **The follow-up task** compares the versions again and rebuilds if an edit was missed.

If Redis is unavailable, the pipeline fails open and triggers a build immediately. I compared the two failures: an extra build takes about a minute, while a skipped build leaves a published post invisible and nobody notices.

## Moving to Next.js without changing the contract

The blog later moved with Arya 2.0 to a [Next.js](https://nextjs.org) frontend. Features I'd built into the static build, like metadata and sitemaps, became part of the framework.

I built the public blog API, the TipTap to HTML renderer and the Next.js blog reader for this move. The contract stayed the same: same URLs, same slug history and same structured data. That let search engines keep seeing the same pages after the frontend changed.

During the cutover window, the site returned HTTP 503 with a `Retry-After` header. That tells crawlers the outage is temporary, so they should come back later rather than treat the pages as gone.

I also made the Next.js build handle an unreachable blog API, so a backend outage couldn't block a frontend deploy.
