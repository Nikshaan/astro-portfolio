The web platform was invisible to Google. The site was a client-rendered React single-page app on a static host, so crawlers saw an empty shell, and I had two days to fix that without adding expensive server infrastructure.

During my software engineering internship at a career-tech startup, I built the platform's self-hosted blog end to end, including the CMS, public reader, SEO layer and automated publishing pipeline. I shipped the first working version within those two days, followed by a scalability rework so the static prerender pipeline would hold up as content volume scaled. The only additions were a deploy hook and a rebuild-delay setting, for about $0 of added infrastructure.

The brief also required a real `/blog` subfolder on the main domain, strong search discoverability and no third-party CMS lock-in. And because the frontend was a client-rendered app on a static host, the host couldn't return native server 301 redirects or 404 status codes.

## What a static host can't do

| SEO needs | The static host gives | What I built instead |
| --- | --- | --- |
| Real HTML for crawlers | An empty page, until JavaScript runs | Every post prerendered to static HTML at build time |
| Per-post titles, descriptions and social cards | One shared head section for every page | Head tags and structured data baked into each page |
| 301 redirects for renamed posts | No per-URL redirects | A slug history and a redirect page for every old URL |
| Real 404s | The app shell, with a 200, for any unknown URL | `noindex` not-found pages for removed posts |
| Fresh content on publish | Nothing changes until a redeploy | A publish-triggered, debounced rebuild |

The obvious alternative was to move the whole frontend to a server-rendered framework like Next.js. That didn't fit the brief. Next.js server rendering needs a running server, and the brief ruled out adding any new hosted service. Re-platforming the entire app for a blog of a couple of dozen posts would also be a massive undertaking. So I kept the stack and solved each gap at build time.

If you're stuck with a client-rendered app on a static host, my advice is to move every decision a server would normally make, like redirects, 404s and head tags, into the build. Once the build owns those, the static host stops being a problem almost everywhere. The one thing it still can't give you is a true 301.

Everything lives inside the platform's existing stack. That's FastAPI, Postgres, Redis and Celery on the backend, and the React app's own build on the frontend.

The key decision was how to store a post, and I kept two forms of it.

- [TipTap](https://tiptap.dev) JSON is the source of truth. It's structured, so the editor always reopens exactly what was saved.
- Sanitised HTML is a server-rendered cache. The backend renders the JSON once, adds heading IDs for the table of contents, and sanitises it against an allowlist (`nh3`). That way, the reader never renders raw user HTML.

## SEO-grade HTML from a client-side app

I wrote a build-time prerender that renders the real React blog pages to static HTML, so the page a crawler reads and the page a user sees come from the same components. Each prerendered page carries:

- Its own title, meta description and canonical URL
- Open Graph tags for link previews
- `Article` structured data for rich results, plus `FAQPage` markup, which helps machines understand the page even though Google stopped showing FAQ rich results for most sites in 2023
- A table of contents built from the heading IDs
- An entry in a generated `sitemap.xml`

The hard part is making the static HTML and the live app match exactly. If there's any difference, React throws the page away and re-renders it. I injected the hashed CSS from Vite's build manifest so pages don't flash unstyled. Blog routes load eagerly so the server and client trees match. And date formatting is pinned to one timezone, so the build machine and the reader's browser print the same date.

## Redirects and 404s without a server

URLs change. A writer renames a post, a post gets unpublished, or an old link lives on in Google's index. On a static host whose catch-all rule serves the app shell for any unknown URL, each of these returns a 200 instead of a redirect or a 404, and that quietly hurts rankings. So I moved these decisions into the build.

- When a post's slug changes, the old one goes into a slug history. At build time, each old URL gets a tiny page that instantly redirects to the new one.
- Unpublished posts get a not-found page marked `noindex`, so they drop out of search instead of lingering.
- Paginated index pages and per-category archives, with previous and next links, make every post reachable through links and not just through the sitemap.
- To avoid duplicate pages, `/blog/page/1` redirects to `/blog`, and drafts never show up in any public listing.

## Publishing without a human

On a static site, publishing changes nothing until the site rebuilds. I wanted "Publish" to mean live. Nobody should have to run a deploy, and five quick edits shouldn't trigger five full builds.

1. Publish marks a rebuild as pending in Redis.
2. A 45-second debounce window collects further edits, so a burst of changes becomes one build.
3. The deploy hook fires, and the pending flag clears only after it succeeds, so a failed trigger is never lost.
4. A guaranteed follow-up job in Celery catches edits made while a build was already running.

The most important decision was to fail open when Redis is unavailable. That was a deliberate call, and I made it by comparing the two ways this can fail. A redundant build costs a minute, while a silently skipped one leaves a published post invisible with nobody noticing.

The build fetches posts in concurrent batches with strict timeouts. Fetch time still scales with the number of posts, but concurrent batching prevents build latency from bottlenecking publication.

## Results

Dozens of posts across multiple categories went out through this system. Each one was prerendered, listed in the sitemap and carried its own structured data. When the web platform later transitioned to Next.js, all posts and their URLs carried over intact with zero indexing drop.

## Trade-offs and what's next

- Redirect pages aren't true 301s. They redirect instantly, and search engines typically follow them, but a real 301 is the cleaner signal. That was the cost of a static host with no edge layer.
- Every publish redeploys the frontend build. The deploy hook triggers the static-site build from `main`, which builds the app, then the SSR bundle, then prerenders every blog page. That's simple and cost-effective. As content volume expands, adopting incremental static regeneration would avoid rebuilding unaffected pages.
- Images go up as uploaded. Automatic resizing and WebP conversion at upload time is the next performance win.

## Built with

React 18 and Vite with a custom Node prerender, [react-helmet-async](https://github.com/staylor/react-helmet-async) for head tags, [TipTap](https://tiptap.dev) for the editor, and FastAPI, SQLAlchemy, Alembic, Postgres, Redis and Celery on the backend, hosted on Render.
