At Mentoria, I worked on moving Arya, an AI job-search platform, to a rebuilt version on [Supabase](https://supabase.com). This wasn't a normal upgrade. The authentication system, data model and several product rules had changed, so the data had to be translated, not just copied.

Some of the new tables were also write-once, which meant a bad write couldn't simply be edited later. Most users would never see the migration, but they would notice if their account or history was wrong.

So I started with one question: **what happens if this fails halfway through?**

## The main decisions

I made four decisions early, and most of the system followed from them.

### 1. Migrate from a frozen source

I considered running both systems side by side, but keeping both in sync would have added another translation layer for a one-time move. It could also have caused both systems to act on the same data.

Instead, the old system was frozen, and every stage read from a snapshot taken at one cut-off time. That kept all tables consistent with each other and meant a stage could safely run again.

### 2. Create accounts before users return

Accounts could have been created when users next signed in, but their existing records needed something to point to immediately. I created accounts in advance and kept the original user IDs, so relationships across the data stayed valid.

### 3. Make every stage idempotent

An idempotent stage leaves the database in the same state whether it runs once or several times. Users kept their existing IDs, and other rows got deterministic UUIDv5 IDs generated from their table and original key:

```python
def row_id(table: str, legacy_key: str) -> uuid.UUID:
    return uuid.uuid5(MIGRATION_NAMESPACE, f"{table}:{legacy_key}")
```

If a stage ran again, it produced the same keys, and the database skipped anything already present.

### 4. Don't trust row counts alone

A count can match while the values are wrong. Verification had to check both completeness and correctness, so I treated it as part of the pipeline from the start.

Every stage ran as a dry run by default and printed what it would write. Writing to the database required an explicit `--execute` flag.

A small [SQLite](https://www.sqlite.org) ledger recorded each run, including its stage, status, [Git](https://git-scm.com) commit and source snapshot. This made it easy to see what had happened and which code and data produced it. The ledger was only for reporting and resuming. Correctness still came from the deterministic IDs and database constraints.

## How a batch loads

Each loader processed users in fixed-size batches using keyset pagination. Unlike `OFFSET`, keyset pagination jumps directly to the next ID through the index, so later pages don't get slower.

For each batch, the loader:

1. Translated the old rows into the new format.
2. Bulk-loaded them into a temporary table with `COPY`.
3. Inserted them into the real table, skipping conflicts.
4. Compared the returned keys with the keys it had sent.
5. Committed the batch and updated the ledger.

The core SQL looked like this:

```sql
INSERT INTO target_table (...)
SELECT ... FROM temporary_table
ON CONFLICT DO NOTHING
RETURNING id;
```

`COPY` is fast, but it can't handle conflicts by itself. The temporary table gave me both fast loading and safe inserts.

I chose insert-or-skip over upserts because an upsert can silently overwrite existing data during a re-run. With insert-or-skip, a second run writes nothing new, and the returned keys show exactly what changed.

## Handling bad data

One bad record shouldn't stop an entire migration, but it shouldn't disappear either.

When the database rejected a batch, the transaction rolled back and the loader split the batch in half. It kept splitting until it found the bad user, then moved that user to quarantine with a reason. Connection failures and code bugs stopped the stage, because retrying wouldn't fix them.

Quarantine also had a limit. If too many records failed, the guardrail stopped the stage and refused to report success. Stages that touched write-once data had a stricter limit.

## Creating accounts safely

The auth provider's real rate limit wasn't documented, and I didn't want to guess one. I used an AIMD limiter, the same basic idea TCP uses for congestion control:

```python
if throttled:
    limit = max(1, limit // 2)
else:
    limit = min(cap, limit + 1)
```

Each success allowed one more request in flight, and each HTTP 429 cut the limit in half. Since the user IDs were fixed, a retry couldn't create a second account.

## The bug the guardrail caught

During the production run, a guardrail stopped one stage because far too many records were being quarantined. I didn't re-run anything until I understood why.

I reproduced the failure read-only, using the loader's own database connection. The cause was a parameter inside `jsonb_build_object`. [psycopg](https://www.psycopg.org) 3 sends SQL and values separately, so [Postgres](https://www.postgresql.org) has to infer each value's type. This function accepts many types, which left Postgres with nothing to infer from.

The error rolled back the transaction, so records that should have been updated ended up in quarantine. My tests had missed it because they mocked the database, and a mock can't reproduce this kind of database-level behaviour.

The change itself was small:

```diff
- jsonb_build_object('reason', %s)
+ jsonb_build_object('reason', %s::text)
```

I then re-ran the stage. Because the pipeline was idempotent, recovery didn't need a separate repair script.

Without the guardrail, the run could have looked successful while leaving bad data behind. It turned a silent failure into a clear stop, and it taught me that database code needs integration tests against a real database.

## Proving the data was right

I used two levels of verification.

**Reconciliation** checked that the core tables balanced at the same cut-off time:

```text
read = written + already_present + skipped + quarantined
```

Every source row had to be accounted for.

**Field-level verification** recalculated a sample of users' data from the source using the new platform's own logic, then compared the results with what was stored. Because it didn't reuse the loader's logic, it was less likely to share the loader's blind spots.

I also ran staged pilots and crash drills. In the drills, I killed the loader mid-stage with `kill -9` and ran it again. It had no chance to clean up, which made it a good test of whether a re-run could really recover safely.
