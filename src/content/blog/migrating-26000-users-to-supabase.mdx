During an infrastructure overhaul at a career-tech startup, I led the overnight database migration from our legacy PostgreSQL backend to a modern Supabase architecture. The cutover transferred over 26,000 user accounts, 100k+ job applications, hundreds of thousands of interaction records, and thousands of OAuth email connections. I built and owned the migration toolchain, executing every cutover stage through the planned maintenance window.

Nobody had to create a new account, reset a password or re-upload a résumé. Users authenticated through their existing OAuth providers as before, background workflows resumed seamlessly, and customer support received zero migration-related tickets.

**At a glance**

- Over 26,000 accounts provisioned in under 10 minutes with zero schema errors
- Every stage safe to kill and re-run: a second run writes zero rows
- Thousands of OAuth integrations carried over without requiring user re-authentication
- Zero orphaned records: 100% data reconciliation across relational boundaries

## The problem

The new architecture wasn't just an upgrade; it was a full platform rebuild featuring a modernized stack, revised UI, new authentication layer, and refactored schema.

| | Legacy Platform (v1) | Modern Platform (v2) |
| --- | --- | --- |
| Sign-in | Custom OAuth implementation | Supabase auth (GoTrue) |
| Billing | Daily usage quotas | Usage credits; write-once ledgers |
| Outreach | Single denormalized tracking table | Normalized applications, contacts, and message events |
| Stack | FastAPI + Postgres | FastAPI + Supabase Postgres + Next.js |

Users expected their existing sign-in credentials to continue working, active OAuth email tokens to remain connected, and ongoing application sequences to pick up seamlessly. Two constraints made this challenging: the legacy system had to remain live until the exact cutover point, and several v2 ledger tables were write-once, meaning erroneous writes could not simply be updated in place.

## Four decisions

| Decision | What I rejected | Why |
| --- | --- | --- |
| One closed window from a frozen copy of the source | Running both systems side by side | Dual writes risk race conditions and duplicate recruiter messages. An atomic cut-off ensures strict relational consistency. |
| Pre-create every account with deterministic IDs | Creating accounts on first sign-in | Relational records like applications and billing history require parent account foreign keys immediately. |
| Insert-or-skip with deterministic IDs | Upserts | Any stage can be halted and restarted safely; subsequent runs write zero redundant rows. |
| Verify with v2's own validation logic | Trusting simple row counts | Matching counts can easily mask malformed or incorrectly defaulted values. |

The risk I designed around most was the billing stage. Financial ledger tables in v2 are write-once. Before billing wrote them, a wipe and reload was still possible, but once committed, the only way back was the pre-load snapshot. So billing carried a quarantine limit of zero, executing after applications, referrals, and credits had fully loaded and verified. Verification ran immediately after.

## A loader you can kill at any moment

The toolchain is a Python orchestration suite built from 16 discrete stages that extract slices of the legacy schema and transform them into 36 target tables in the new architecture. The stages run in dependency order, because relational foreign keys require parent rows to exist prior to child insertion.

Each stage runs as a dry run by default, preventing unintended writes during testing. Every stage is designed to be stopped at any moment and safely restarted, because every row's primary key is deterministic. Accounts retain their legacy identifiers, and relational records receive a deterministic UUIDv5 derived from the table name and legacy identifier. Batches are ingested using `COPY` into staging tables before executing an `INSERT … ON CONFLICT DO NOTHING` statement into production tables, ensuring reruns skip pre-existing rows without side effects.

Each step writes only what it can prove, and automated guardrails halt execution immediately upon encountering data anomalies rather than writing corrupt state.

In testing drills and final cutover, mid-stage terminations with `SIGKILL` produced identical databases upon rerun with zero duplicate records.

## No re-login, no reconnect

**Accounts.** Every account was provisioned through Supabase's Admin API before sign-in reopened. To prevent API throttling, the migration worker used an adaptive token-bucket rate limiter that halved request concurrency on HTTP 429 responses. Inactive accounts with historical transactional records were preserved with disabled authentication to maintain ledger integrity.

**OAuth Sessions.** Third-party OAuth tokens were re-encrypted with the new application key using authenticated Fernet cipher suites, then verified for integrity. Active integrations carried over seamlessly, while stale sessions were flagged for standard re-authorization.

**Automated Queues.** Paused message queues resumed gradually across a staged schedule to prevent outbound connection bursts.

## Reshaping the data

Most of the work wasn't moving rows. It was translating them into a different model.

| --- | --- | --- | --- |
| Outreach | Single denormalized tracking table | Normalized applications, contacts, and message events | One application per user and job, one contact per recipient. Duplicate events were coalesced to preserve history without redundant messaging. |
| Résumés | Freeform JSON with ad-hoc revision histories | Versioned schema records with strict schema constraints | Historical entries were transformed through v2 validation functions, with cryptographic source hashes attached for verification. |
| Billing | Daily usage quotas | Usage credits | Legacy subscription tiers were deterministically mapped to equivalent usage credit balances calculated from remaining billing period duration. |

## Proving it was right

Row counts don't prove the data is correct. Reconcile compared every core table against the source at the same cut-off instant. Fieldcheck went further. It re-derived each field from legacy data using v2's own validation functions and compared the result against the target database, avoiding shared blind spots.

Multi-phase staging pilots against sampled datasets uncovered several undocumented legacy schema edge cases. For instance, legacy records occasionally contained thread status flags without corresponding child event rows; mapping rules were refined to infer status deterministically from historical metadata rather than assuming modern foreign-key guarantees.

## The cutover night

The migration was scheduled during a planned overnight maintenance window to minimize user impact. Execution milestones from the run log:

<Figure
  src={migrationCutoverTimeline}
  alt="Cutover timeline from the source freeze through verification, validation, and smoke tests."
  caption="The execution flow: freeze, accounts, core entities, verification guardrail, and validation."
/>

1. **Source Freeze & Backup:** A fresh logical dump of the legacy database was taken and locked read-only, establishing an immutable cut-off boundary.
2. **Auth Provisioning:** The administrative auth worker ran concurrently, safely creating user accounts with deterministic IDs across the target schema in minutes.
3. **Core Entity Ingestion:** Candidate profiles, structured résumé histories, and application records loaded in strict dependency sequence.
4. **Relational Integrity & Balances:** Applications, event timelines, and billing credit balances were imported under idempotent transactions.
5. **OAuth Token Verification & Error Handling:** During token validation against external provider endpoints, an automated guardrail triggered due to a type casting discrepancy in the driver query under psycopg 3, causing status updates to safely roll back rather than corrupting connection states. Because every stage was idempotent, isolating the query parameter type fix allowed the verification worker to re-run smoothly without dirty data.
6. **Reconcile & Smoke Testing:** End-to-end data validation confirmed zero row discrepancies across source and destination before DNS cutover and public reopening.

For the migration, prioritizing idempotency paid massive dividends. Every stage could be re-run safely, meaning any encountered issue was resolved by re-running a stage rather than undertaking manual database surgery.

## Trade-offs and what's next

- Insert-or-skip makes re-runs free but corrections expensive. Changing a mapping after load means reloading the affected users. Next time, a mapping version stamped on every row would let a fix target exactly what changed.
- Fieldcheck holds its comparisons in memory, so in production it verified a sample instead of every user. Streaming would give full coverage at this scale.
- Parallelism was manual, and the heaviest stages were sliced by hand. Built-in workers with a connection budget would make the next migration faster.

It all ran on Python 3 (async), psycopg 3 with `COPY`, Postgres on Supabase, the GoTrue Admin API, Fernet encryption for tokens, boto3 for S3, a SQLite run ledger, and pytest.
